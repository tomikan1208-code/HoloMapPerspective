# 0.6.0: 色・大きさ・家の読み込み・更新速度

確認日: 2026-11-07。Windows 11、Java 25、Paper 26.3 build 243、NVIDIA RTX 3050、Python 3.13 / ModernGL / Pillowで検証しました。

## 修正内容

- Sparxie: サーバーにあったOBJは画像テクスチャを含まず、参照MTL名も実ファイルと違いました。元PMXからUV・拡散色・画像7枚を取り出す準備ツールと、テクスチャ付きGPU形式 `HMAPTEX1` を追加しました。52,228三角形の静止モデルです。
- 大きさ: 以前は直方体の最短辺にモデルの最長辺を合わせていました。全アニメーションフレームのXYZ範囲と直方体の3軸で一様な拡大率を決め、縦長のモデルを縦長の箱へ収めます。Sparxieは2×4×2・余白0.82で高さ約2.55ブロックになり、以前の1.64ブロックから拡大します。横へ広がる腕も収めるため、高さ4ブロック全体には伸ばしません。
- 家: 元OBJは約617MB、元Blender形状は約855万三角形あり、上限300万を超えていました。正本Blenderを保存せずメッシュのコピーを軽量化し、637,073三角形・約30.6MBのGPU用データを作成しました。Minecraft用コピーから `EX_前面道路_幅7_1m_参考` だけを除き、参考道路の幅に引っ張られて家が小さくなるのを防ぎました。家の材質はベースカラーを使用します。
- 更新速度: `render-fps` / `animation-fps` を20へ切り詰めていた処理を修正しました。ワールド・プレイヤーの取得はサーバースレッドのまま、描画と地図送信を独立した時間スケジューラで最大60回/秒実行します。Paper 26.3の地図差分を6面分まとめてネイティブのbundle packetで送ります。
- 横移動: 直近2回の位置と時間から移動速度を求め、次の位置受信まで最大1tick分を予測します。大きな瞬間移動、200msを超えたサンプル間隔は予測せず、古い視点を大量にキューへ積まない設計です。
- Bukkitの自動地図送信が空白の旧キャンバスでネイティブ画像を上書きしないよう、該当プレイヤーの自動色パッチだけを抑止します。しばらく表示範囲を離れて戻ると、差分基準をリセットして全地図を再送します。
- GPUに最大8メッシュを保持し、家・Sparxie・デモを同時表示すると毎回モデルと画像を読み直す問題を防ぎました。

## 検証結果

`gradlew.bat build gpuVerificationJar` 成功。JUnit 18件、失敗0件。`tools/test_gpu_protocol.py`、実GPUの `tools/test_gpu_textures.py` が成功しました。後者はUVの上下・RGB色・透明部分・10メッシュを順に使った際の画像参照と解放を検証します。既存形状の実GPU比較42視点も成功しています。

オフスクリーン描画ではSparxieの赤い服・白い髪・透明背景を確認しました。カラー画像は16,455色、家の描画も透明以外の画素175,238個があり、空白にならないことを確認しました。プレビューはプロジェクト内 `prepared-models/` に保存しています。Minecraftの地図パレットへ変換する前の画像です。

独立したテストサーバー `build/gpu-verification-server` で、前回の途切れ再現、76視点、同じ更新内での各タイルの画像整合性、Bukkitの旧画素パッチ抑止、ネイティブ地図パケット構築を検証し、1,730アサーションを通過しました。ユーザーのワールドに検証用表示を作っていません。

| 表示モデル | 単独、4×4×4での変更パケット束/秒 | 3モデル同時の変更パケット束/秒 |
| --- | ---: | ---: |
| デモ | 58.54 | 54.63 |
| Sparxie | 53.50 | 35.22 |
| home | 41.45 | 39.02 |

移動する模擬視点を20TPSで与え、60fps時計で実GPU描画し、実際のPaperネイティブパケットをメモリ上の受信先で数えた各約5秒間の値です。複数表示時のSparxieとデモは2×4×2、家は4×4×4です。同じ画素が続く場合は送信を省くため、パケット束の回数は描画完了回数より少なくなる場合があります。通信・Minecraftクライアントの表示fpsを測った値ではなく、全条件で60fpsを保証する結果でもありません。

## 確認できていない範囲

ゲームクライアントを操作する機能が利用できず、ゲーム画面での色・揺れの目視確認と、実クライアントの表示fps測定は未実施です。サーバーで分からないカメラの歩行揺れ、ネットワーク遅延、他の物体や雨との正確な前後関係は残る制約です。初回テクスチャ読み込みや地図色キャッシュの準備中にも一時的な速度低下があり得ます。
